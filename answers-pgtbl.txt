q2
Each leaf in the vmprint output corresponds exactly to one row from print_pgtbl, 
because both are reading the same PTE; vmprint just also shows the two intermediate pointer PTEs that pgpte hides. 
At VA 0x0 is the first text page, mapped read-execute-user (RXU) with the accessed bit (A) set, 
since the program counter has passed through it; it permits instruction fetch and data reads but forbids writes, 
so the process cannot modify its own code. VA 0x1000 is the second text page, also RXU, but with A clear, 
meaning the hardware page walker has not yet resolved it through the TLB, so it has not been read or executed. 
VA 0x2000 holds .data and .bss, mapped RWU with no execute bit — writable by the program but not runnable as instructions. 
VA 0x3000 is the stack guard page: it is valid and marked RW, but crucially lacks PTE_U, 
because uvmclear does *pte &= ~PTE_U rather than invalidating the PTE, 
so any user-mode access to it raises a page fault while the kernel retains access. 
VA 0x4000 is the base of the user stack, mapped RWU with both A and D set, recording that it has been both accessed and written. 
At the top of the address space, VA 0x3fffffe000 is TRAPFRAME, mapped RW with A and D set and no PTE_U, 
so the trampoline can save and restore registers but user code cannot forge one; 
VA 0x3ffffff000 is TRAMPOLINE, mapped RX with A set and no PTE_U, 
letting a trap jump to uservec while preventing user code from executing it directly. 
Note that physical addresses are not consecutive (0x87f22000 then 0x87f1f000) because kalloc returns pages from a LIFO free list, 
and that 0x3000 shows up in print_pgtbl as perm 7 and 0x3fffffe000 as 0xc7;
the same values vmprint renders as the truncated RW and RW strings.
